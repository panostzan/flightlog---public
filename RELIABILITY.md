Flightlog starts automatically when the Windows user who installed it signs in, including the first sign-in after a reboot. It does not run before login, as a Windows service, or under an administrator account. Foreground collection needs the user's interactive desktop. It runs hidden and does not open Chrome or the Galaxy.

Install or update with `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\install-startup.ps1`. This publishes a separate runtime under `.tools`, gracefully stops a reachable existing backend, registers the per-user Task Scheduler task `Flightlog-<Windows user SID>`, and starts it immediately. The task uses an interactive login and limited privileges, without a stored password. Each update publishes to a new directory before stopping collection, so running binaries are not overwritten. Keep this repository and its workspace .NET SDK at their current paths; rerun installation after moving them or updating backend code. Frontend assets continue to come from `backend`.

The task has no execution time limit, runs on battery, and is not stopped when switching to battery. Overlapping task launches are ignored; the backend also rejects a second instance for the same data directory. A failed task is retried up to three times at one-minute intervals. This covers startup/process failures, not every possible hang. An intentional API shutdown exits successfully and does not trigger failure retries. The next login starts it again. `Flightlog.cmd` also starts the installed task when the backend is absent.

The task pins the data directory selected during installation: `FLIGHTLOG_DATA_DIR` if set, otherwise `%LOCALAPPDATA%\Flightlog`. Use the same override when invoking manual scripts. Existing capture preferences and exclusions are preserved. A previously paused Windows collector remains paused. Chrome capture requires Chrome to be running with the enrolled extension enabled and unpaused; the task does not launch Chrome, enable extensions, or change their settings.

A companion `Flightlog-<Windows user SID>-Recovery` task checks every five minutes while this user is signed in. It launches a small Windows GUI executable, built from `scripts/RecoveryHost.cs` with the installed .NET Framework compiler. The launcher runs PowerShell with `CreateNoWindow`, waits for completion, and returns its exit code to Task Scheduler. This avoids the console flash possible when Task Scheduler starts PowerShell directly with `-WindowStyle Hidden`. The executable is stored under `.tools/recovery-host-*`; keep the directory referenced by the task. Updating recovery alone with `scripts/install-recovery.ps1 -DataDirectory <data directory>` does not restart the active collector.

If the backend left its running marker behind and the main task is ready, recovery starts the main task again. This covers unexpected stops beyond the three immediate failure retries. Graceful shutdown removes the marker, so `scripts\stop.ps1` remains stopped until login or a manual start. Recovery does not detect a hung process, wake the computer, or backfill missed activity. Removing startup removes both tasks.

To verify after reboot:

1. Sign in to the same Windows account. Open Chrome with the existing enrolled extension enabled.
2. Wait approximately 30–60 seconds for Chrome's periodic observation/delivery. A large queued backlog may take longer.
3. Double-click `Flightlog Health.cmd`, or run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\health.ps1` from this folder.
4. Expect `Backend: running`, `logs: ok`, `windows: recording`, and `chrome: recording`. Run it again about 35 seconds later and confirm both last-observation timestamps advance. Window locks, pauses and sleep can legitimately stop fresh samples.
5. If the backend is unreachable, run `Flightlog.cmd`. Inspect the task in Windows Task Scheduler and the logs described below if it still fails. A running task alone is not proof of recording.

The health command reads the authenticated existing `/api/v1/status` endpoint without printing its token. `-Json` returns structured status. Exit code 0 means both sensors are recording and diagnostic logging is healthy; 2 means the backend is reachable but one of those conditions is unmet; 1 means it is unreachable, incompatible, or its local settings cannot be read.

`recording` requires a newly committed state observation during this backend run, observed within 5 seconds for Windows or 75 seconds for Chrome, with a recent monotonic receipt time as well. Replaying already stored IDs does not refresh health. Delivering an old backlog does not count as current recording. Navigation events alone cannot establish Chrome state freshness. Background, excluded and unavailable state observations still demonstrate that the Chrome sensor is producing records; this indicator does not claim that a person is browsing or paying attention.

Other reported states include `starting`, `waiting_for_observation`, `paused`, `locked`, `disabled` for `-NoCollector`, `not_enrolled`, `storage_error`, `session_notifications_unavailable`, and `stale_or_disconnected`. Stale Chrome means fresh state has not arrived; it does not distinguish a closed browser, disabled extension, queue trouble, sleep, or network failure. A received pause boundary is reported as paused until a newer state arrives. Diagnostic log write failures appear as `logs: write_failed`.

Persistent diagnostics live in the data directory:

- `backend.jsonl`: UTC timestamps, backend process IDs, fixed lifecycle/health/error codes, exception type and numeric error code. Includes startup begin/ready, shutdown request/complete, storage failures/recovery, Windows lock/resume/health changes, Chrome freshness changes, and fatal errors. It excludes tokens, event bodies, titles, URLs, queries, exception messages, and stack traces. Files rotate at approximately 2 MiB, retaining three previous files.
- `launcher.jsonl`: task wrapper start, exit/error and exit code. It also catches failures before the backend can start, such as a missing runtime. It rotates at approximately 1 MiB with one previous file.
- `backend-running.json`: a marker for the current run. A completed shutdown removes it. A later startup finding it logs `previous_run_unclean_or_shutdown_incomplete`; this records uncertainty and does not assert whether the cause was a crash, power loss, forced task termination or interrupted shutdown. No program can write a final log after power is lost. Older runs from before logging was installed have no marker.

Use `Get-Content "$env:LOCALAPPDATA\Flightlog\backend.jsonl" -Tail 20` to inspect recent diagnostics, adjusting the path for a custom data directory. If the data directory itself is unwritable, file logging cannot succeed; the launcher exits nonzero and Task Scheduler exposes the failure. Persistent logs are bounded diagnostics, not activity records.

`scripts\stop.ps1` requests a graceful backend shutdown. Chrome can continue buffering; pause it separately if desired. To remove future login startup, run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\install-startup.ps1 -Remove`. Remove startup first and then run `scripts\stop.ps1` if you also want to stop the current collector. Removal keeps observations and settings.

Collection restarts use fresh sensor sessions. Downtime, missed confirmations and clock uncertainty remain unknown under the existing reconstruction algorithm; startup and diagnostics never backfill activity.

Browser connection: an unpaired Galaxy page offers **Open Flightlog**, a `flightlog://open` link registered for this Windows user by `scripts\register-protocol.ps1`. The handler invokes only the fixed local launcher; it does not pass URL arguments to a shell. The launcher reads the protected local settings and opens the default browser already connected. Tokens are not exposed by a public API or placed in the protocol registration. Browser permission to open the local app may be required. If the handler is missing, double-click `Flightlog.cmd` once to register it and connect. Connection persists in that browser profile; another profile or cleared site data needs the launcher again. The inspection page retains a collapsed advanced manual connection for diagnostics.
